02 / 請求的時間線

一次請求的三段工作

先把 token 想成模型讀寫文字的小單位。一段回答會依序出現許多 token。

QueuePrefillDecode
排隊

請求到達後可能先等待排程；排隊時間與模型實際處理輸入的時間可以分開觀察。

不同觀測位置的事件與計時方式可能不同。
處理輸入

Prefill 處理輸入的 prompt，建立後續生成所需的狀態，並形成第一個輸出 token。

這裡介紹自回歸文字生成的概念；不假設服務一定用一整批一次完成 prefill。
接續生成

Decode 接續生成後面的 token；後續輸出會依賴先前的上下文與已生成的 token。

這是自回歸生成的順序關係，不代表每次網路串流都只傳一個 token。

03 / 延遲指標

首個 token 與後續節奏

同樣是慢，可能是很久才開始，也可能是開始後一小段一小段等。

TTFT

首個 token 的等待時間（TTFT），在這裡指服務前端接收請求到收到第一個輸出 token 的時間。

vLLM v0.11.0 V1 前端量測邊界，包含前端輸入處理與可能的排隊；不是把 prefill 單獨計時。
ITL

相鄰輸出 token 的間隔（ITL）看的是後續 token 到達的節奏。

不要把相鄰間隔的分布和每個請求的平均 TPOT 當成完全相同的統計量。
完成時間

這裡的完成時間從服務前端收到請求算到最後一個 token。

客戶端所見的完成時間還可能包含網路與前端處理，不能混用計時邊界。

04 / 推論狀態

KV cache 保存哪些東西？

想像一本筆記：保留已算好的中間狀態，後面可以接著用。

保留狀態

KV cache 保存先前 token 已算出的注意力 key、value，讓後續生成可以使用這些狀態。

保存的是模型中間狀態，不是把整篇已生成的回答當作快取結果。
分塊管理

PagedAttention 把 KV cache 以區塊管理，可隨序列長度配置，區塊不必在記憶體中連續。

原論文設計；這個機制本身不保證特定請求會降低固定比例延遲。
比對條件

在這份 vLLM 設計中，快取比對用前綴和區塊內的 token 等資訊，且只快取完整區塊。

意思相似不表示前綴一致；這是指定版本文件的實作條件，不套用到所有框架。

05 / 跨請求重用

共同前綴可以少算一次

想像兩個人拿同一份手冊問不同問題。下圖只標出共同的開頭。

請求 A手冊開頭共同內容問題 A
請求 B手冊開頭共同內容問題 B
可重用

自動前綴快取（APC）讓新請求重用相同前綴的可用 KV 狀態，減少該段 prefill 的重複計算。

須有相容且仍可用的共同前綴；示例不代表全程都命中。
仍需生成

APC 減少共同前綴的輸入處理工作，並不直接縮短後續每個新 token 的 decode 計算。

不能由 APC 命中推出 ITL 必然下降，也不能推估固定延遲改善比例。
何時幫助小

沒有可重用前綴時，不能靠該段快取省下計算；若等待主要來自長輸出，整體改善也可能有限。

實際效果取決於工作負載、排程與快取狀態。

06 / 多個工作節點

有快取的節點也可能排隊

教學情境：A 有相容的前綴但很忙，B 沒有前綴但比較空。你還需要知道什麼，才能決定送去哪裡？

WORKER A有前綴，有排隊
WORKER B沒前綴，較空閒
重用

若節點已保存相容前綴，將請求送往該處可能重用已有工作。

假設路由能取得合適的快取資訊；請求放置與選擇不同模型是兩件事。
負載

已有快取的節點可能排隊；負載感知路由會把重用效益和節點當下負載一起考慮。

範例說明取捨，不宣稱最空閒節點一定較快或任一策略必然獲勝。

07 / 互動小實驗

排隊與生成如何改變等待？

先移動排隊時間，再切換前綴命中。觀察哪個結果改變。

TTFT600 ms
ITL30 ms
完成時間810 ms
排隊Prefill後續生成

教學模型：200ms 排隊 + 400ms prefill，首 token 後還有 7 個間隔。

教學假設，非實測。 輸出固定 8 個 token，假設每次輸出一個 token。命中只把示意 prefill 從 400ms 調為 150ms。完成時間 = TTFT + 7 × ITL；省略網路與其他開銷。
